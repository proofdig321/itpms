As we approach phase close, here are a few backend improvements we'd like to suggest based on integration experience:

---

1. TASK STATUS ENDPOINTS (High Priority)

The following are wired on the frontend but not yet implemented:

  POST /api/v1/tasks/{id}/progress   — body: { percentComplete, remarks, userId }
  POST /api/v1/tasks/{id}/hold       — no body
  POST /api/v1/tasks/{id}/resume     — no body
  POST /api/v1/tasks/{id}/cancel     — no body

These are needed for the task lifecycle to work end-to-end.

---

2. PROJECT STATUS ENDPOINTS (High Priority)

  POST /api/v1/projects/{id}/archive — no body
  POST /api/v1/projects/{id}/close   — no body

---

3. CONSISTENT ENDPOINT NAMING

Currently tasks use GET /api/v1/tasks/project?projectCode= while all other modules
use GET /api/v1/{module}?projectCode=. Please consider aligning to:

  GET /api/v1/tasks?projectCode=ITP-2026-0001

This matches the contract and reduces confusion.

---

4. VALIDATION ERROR FORMAT

Laravel's 422 responses return errors as:
  { "field.0.subfield": ["message"] }

The contract specifies:
  { "success": false, "error": { "code": "VALIDATION_ERROR", "message": "...", "details": {} } }

Wrapping validation errors in the standard error envelope would make frontend
error handling consistent across all endpoints.

---

5. CAMELCASE IN ALL RESPONSES

A few responses still return snake_case fields (e.g. created_at instead of createdAt).
Please ensure all API Resources use camelCase consistently — the frontend mapping
depends on this.
