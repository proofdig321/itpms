# API_CONTRACT.md

## ITPMS Laravel API Contract (Frontend-Aligned Specification)

---

## Core Principle

> The frontend defines the data shapes. The backend must conform — not reinterpret.

Laravel serves as:
- A data provider
- A validator
- An aggregator

NOT a redesign layer.

---

## 1. BASE API STRUCTURE

All endpoints follow:

```
/api/v1/{module}
```

### Standard Success Response

```json
{
  "success": true,
  "data": {},
  "message": null,
  "meta": {}
}
```

### Standard Error Response

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid request",
    "details": {}
  }
}
```

### Pagination Meta (where applicable)

```json
{
  "meta": {
    "currentPage": 1,
    "perPage": 20,
    "total": 45,
    "lastPage": 3
  }
}
```

## 2. PROJECTS MODULE (Entity Layer)

> "What exists?"

### Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/v1/projects` | List all projects |
| GET | `/api/v1/projects/{id}` | Get single project |
| POST | `/api/v1/projects` | Create project |
| PATCH | `/api/v1/projects/{id}` | Update project |
| DELETE | `/api/v1/projects/{id}` | Delete project |

### Project Object

```typescript
type ProjectStatus =
  | "on-track"
  | "at-risk"
  | "delayed"
  | "completed"
  | "not-started";

interface Project {
  id: string;
  projectCode: string;       // Format: ITP-YYYY-XXXX (per FR-PI-002)
  title: string;
  description: string;
  status: ProjectStatus;
  progress: number;          // 0-100
  manager: string;
  startDate: string;         // ISO 8601 date
  endDate: string;           // ISO 8601 date
  createdAt: string;         // ISO 8601 datetime
}
```

### Backend Rules

- `projectCode` must be auto-generated by Laravel per format `ITP-YYYY-XXXX`
- `status` must use exact enum values above
- `progress` must be integer 0–100
- Response must be flat (no nested objects)
- Do NOT rename fields
- Do NOT compute status differently from what frontend sends

## 3. PLANNING MODULE (Relationship Layer)

> "What should happen?"

### Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/v1/planning` | List all milestones |
| GET | `/api/v1/planning?projectCode=ITP-2026-0001` | Filter by project |
| GET | `/api/v1/planning/{id}` | Get single milestone |
| POST | `/api/v1/planning` | Create milestone |
| PATCH | `/api/v1/planning/{id}` | Update milestone |

### Milestone Object

```typescript
interface Milestone {
  id: string;
  projectCode: string;       // References parent project
  title: string;
  description: string;
  status: ProjectStatus;     // Same enum as Projects
  progress: number;          // 0-100
  assignee: string;
  startDate: string;         // ISO 8601 date
  dueDate: string;           // ISO 8601 date
  createdAt: string;         // ISO 8601 datetime
}
```

### Backend Rules

- Planning is a timeline projection of Projects, NOT a copy of the Projects table
- Must support filtering by `projectCode` query parameter
- Do NOT embed full project objects in milestone responses
- Do NOT duplicate project fields into milestone records
- Same status enum as Projects module

## 4. MONITORING MODULE (Aggregation Layer)

> "What is happening at scale?"

### Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/v1/monitoring/summary` | Full dashboard payload |

**Single endpoint returns everything the executive dashboard needs.**

### Response Shape

```typescript
interface MonitoringResponse {
  portfolioSummary: PortfolioSummary;
  statusDistribution: StatusDistribution[];
  milestoneOverview: MilestoneOverview;
  recentActivity: RecentActivity[];
}
```

### PortfolioSummary

```typescript
interface PortfolioSummary {
  totalProjects: number;
  activeProjects: number;
  delayedProjects: number;
  completedProjects: number;
  notStartedProjects: number;
}
```

### StatusDistribution

```typescript
interface StatusDistribution {
  status: "on-track" | "at-risk" | "delayed";
  count: number;
  percentage: number;
}
```

### MilestoneOverview

```typescript
interface MilestoneOverview {
  totalMilestones: number;
  completedMilestones: number;
  overdueMilestones: number;
  averageProgress: number;
}
```

### RecentActivity

```typescript
interface RecentActivity {
  id: string;
  projectCode: string;
  description: string;
  timestamp: string;         // ISO 8601 datetime
}
```

### Backend Rules (CRITICAL)

- Laravel MUST compute all aggregation server-side
- Never send raw project lists to this endpoint
- Never expose database schema
- Treat this as a "reporting engine"
- `percentage` in StatusDistribution must sum to 100 across active projects only
- `recentActivity` should return last 10 events, ordered by timestamp descending

## 5. DATA FLOW CONTRACT

```
Projects API      → raw truth (CRUD)
Planning API      → relational truth (project → milestones)
Monitoring API    → computed truth (aggregated metrics)
```

Frontend mapping:

```
/dashboard/projects     → Projects API
/dashboard/planning     → Planning API
/dashboard/monitoring   → Monitoring API
```

## 6. NON-NEGOTIABLE RULES FOR LARAVEL

### Forbidden

- No frontend-specific field renaming
- No nested relational explosion (no `project.milestones[].risks[]`)
- No "flexible JSON blobs"
- No mixing monitoring logic into Projects controller
- No snake_case in JSON responses (use camelCase)

### Required

- Strict Resource classes (Laravel API Resources)
- Flat, predictable JSON
- Versioned endpoints (`/api/v1/`)
- Consistent enums across all modules
- camelCase field names in all JSON responses
- ISO 8601 date format everywhere

## 7. AUTHENTICATION & RBAC (AD Integration)

When auth is implemented:

```
POST   /api/v1/auth/login
POST   /api/v1/auth/logout
GET    /api/v1/auth/me
POST   /api/v1/auth/refresh
```

Token: Bearer token in Authorization header.

### GET /api/v1/auth/me Response

```typescript
interface AuthUser {
  id: string;
  name: string;
  email: string;
  role: "ict-admin" | "ict-manager" | "project-manager" | "viewer";
  permissions: Permission[];
}

type Permission =
  | "projects.create"
  | "projects.edit"
  | "projects.delete"
  | "planning.view"
  | "planning.edit"
  | "monitoring.view"
  | "wbs.view"
  | "wbs.edit";
```

Frontend uses this response to:
- Show/hide UI elements via `PermissionGate` component
- Display user context in sidebar
- Never filter data or alter business logic

Laravel + Microsoft AD is the security authority. Frontend is presentation only.

## 8. WBS MODULE (Hierarchy Layer)

> "How is work decomposed?"

### Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/v1/wbs?projectCode=ITP-2026-0001` | Get WBS nodes for a project |
| GET | `/api/v1/wbs/{id}` | Get single WBS node |
| POST | `/api/v1/wbs` | Create WBS node (future) |
| PATCH | `/api/v1/wbs/{id}` | Update WBS node (future) |
| DELETE | `/api/v1/wbs/{id}` | Delete WBS node (future) |

### WbsNode Object

```typescript
type WbsLevel = "project" | "phase" | "deliverable" | "work-package" | "task" | "sub-task";
type WbsStatus = "not-started" | "in-progress" | "completed";

interface WbsNode {
  id: string;
  projectCode: string;
  parentId: string | null;
  code: string;              // "1.0", "1.1", "1.1.1"
  name: string;
  description?: string;
  level: WbsLevel;
  status: WbsStatus;
  startDate?: string;
  endDate?: string;
  progress: number;          // 0-100
  assignee?: string;
}
```

### Backend Rules

- Returns FLAT array (not nested) — frontend builds tree
- `code` is auto-generated by Laravel based on hierarchy position
- `parentId` references another WbsNode in the same project
- Supports unlimited depth (per FR-PLN-002)
- Scheduling calculations (critical path, EVM) are backend responsibility
- Frontend only visualizes structure and progress

- `on-track` → GREEN
- `at-risk` → AMBER
- `delayed` → RED
- `completed` → GRAY (neutral)
- `not-started` → GRAY (neutral)

Laravel must store and return these exact string values.

## 11. FRONTEND INTEGRATION ARCHITECTURE

### API Client

All service files must use the centralized API client (`src/lib/api/client.ts`) when calling Laravel:

```typescript
import { apiClient } from "@/lib/api/client";

export async function getProjects(): Promise<Project[]> {
  return apiClient.get<Project[]>("/projects");
}
```

The API client handles:
- Base URL configuration (`API_BASE_URL` environment variable)
- Default headers (Content-Type, Accept)
- Bearer token injection (future AD integration)
- Consistent error handling and formatting
- Response unwrapping (`response.data`)

### Environment Configuration

```
API_BASE_URL=http://localhost:8000/api/v1   # Local Laravel
API_BASE_URL=https://api.itpms.example/api/v1  # Production
```

### Server-Only Enforcement

Read-only services use `import "server-only"` to prevent client-side bundle inclusion.

Mutation services (create/update/delete) will migrate to Next.js Server Actions when Laravel is ready, at which point they will also become server-only.
