# API_CONTRACT.md

## ITPMS Laravel API Contract (Frontend-Aligned Specification)

---

## Core Principle

> The frontend defines the data shapes. The backend must conform — not reinterpret.

Laravel serves as:
- A data provider
- A validator
- An aggregator

NOT a redesign layer.

---

## 1. BASE API STRUCTURE

All endpoints follow:

```
/api/v1/{module}
```

### Standard Success Response

```json
{
  "success": true,
  "data": {},
  "message": null,
  "meta": {}
}
```

### Standard Error Response

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid request",
    "details": {}
  }
}
```

### Pagination Meta (where applicable)

```json
{
  "meta": {
    "currentPage": 1,
    "perPage": 20,
    "total": 45,
    "lastPage": 3
  }
}
```

## 2. PROJECTS MODULE (Entity Layer)

> "What exists?"

### Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/v1/projects` | List all projects |
| GET | `/api/v1/projects/{id}` | Get single project |
| POST | `/api/v1/projects` | Create project |
| PUT | `/api/v1/projects/{id}` | Update project |
| DELETE | `/api/v1/projects/{id}` | Delete project |

### Project Object

```typescript
type ProjectStatus =
  | "on-track"
  | "at-risk"
  | "delayed"
  | "completed"
  | "not-started";

interface Project {
  id: string;
  projectCode: string;       // Format: ITP-YYYY-XXXX (per FR-PI-002)
  title: string;
  description: string;
  status: ProjectStatus;     // Server-computed based on progress
  progress: number;          // 0-100, server-computed from tasks
  manager: string;
  plannedStart: string;      // ISO 8601 date
  plannedFinish: string;     // ISO 8601 date
  createdAt: string;         // ISO 8601 datetime
}
```

### Backend Rules

- `projectCode` must be auto-generated by Laravel per format `ITP-YYYY-XXXX`
- `status` is server-computed — NOT sent in create/update payloads
- `progress` is server-computed from tasks — NOT sent in create/update payloads
- Response must be flat (no nested objects)
- Do NOT rename fields
- Status transitions via explicit endpoints:
  - `POST /api/v1/projects/{id}/archive`
  - `POST /api/v1/projects/{id}/close`

### Milestone Object

```typescript
interface Milestone {
  id: string;
  projectCode: string;       // References parent project
  title: string;
  description: string;
  status: ProjectStatus;     // Same enum as Projects
  progress: number;          // 0-100
  assignee: string;
  startDate: string;         // ISO 8601 date
  dueDate: string;           // ISO 8601 date
  createdAt: string;         // ISO 8601 datetime

```

### Backend Rules

- Planning is a timeline projection of Projects, NOT a copy of the Projects table
- Must support filtering by `projectCode` query parameter
- Do NOT embed full project objects in milestone responses
- Do NOT duplicate project fields into milestone records
- Same status enum as Projects module

## 4. MONITORING MODULE (Aggregation Layer)

> "What is happening at scale?"

### Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|

**Single endpoint returns everything the executive dashboard needs.**

### Response Shape

```typescript
interface MonitoringResponse {
```

```typescript
interface PortfolioSummary {
```

### StatusDistribution

```typescript
interface StatusDistribution {
```

### MilestoneOverview

```typescript
interface MilestoneOverview {
  totalMilestones: number;
  completedMilestones: number;

```

### RecentActivity

```typescript
interface RecentActivity {
  id: string;
  projectCode: string;
  description: string;
  timestamp: string;         // ISO 8601 datetime
}
```

### Backend Rules (CRITICAL)

- Laravel MUST compute all aggregation server-side
- Never send raw project lists to this endpoint
- Never expose database schema
- Treat this as a "reporting engine"
- `percentage` in StatusDistribution must sum to 100 across active projects only
- `recentActivity` should return last 10 events, ordered by timestamp descending

## 6. NON-NEGOTIABLE RULES FOR LARAVEL

### Forbidden

- No frontend-specific field renaming
- No nested relational explosion (no `project.milestones[].risks[]`)
- No "flexible JSON blobs"
- No mixing monitoring logic into Projects controller
- No snake_case in JSON responses (use camelCase)

### Required

- Strict Resource classes (Laravel API Resources)
- Flat, predictable JSON
- Versioned endpoints (`/api/v1/`)
- Consistent enums across all modules
- camelCase field names in all JSON responses
- ISO 8601 date format everywhere

## 7. AUTHENTICATION & RBAC (Azure AD Integration)

The frontend uses Microsoft's MSAL library to authenticate via Azure AD popup. The flow is:

```
User clicks "Login with Microsoft"
    ↓
MSAL popup → Microsoft login page
    ↓
Microsoft returns access_token
    ↓
Frontend sends access_token to Laravel
    ↓
Laravel validates, creates/updates user, returns app token
```

### POST /api/v1/auth/azure-login

Request:
```json
{
  "access_token": "eyJ0eXAiOiJKV1Q..."
}
```

Response:
```json
{
  "success": true,
  "data": {
    "token": "app-bearer-token",
    "user": {
      "id": "uuid",
      "name": "Bheki Simelane",
      "email": "bheki@municipality.gov.za",
      "role": "ict-admin",
      "permissions": ["projects.create", "projects.edit", ...]
    }
  }
}
```

### GET /api/v1/auth/me

Returns current authenticated user (uses Bearer token from header).

```typescript
interface AuthUser {
  id: string;
  name: string;
  email: string;
  role: "ict-admin" | "ict-manager" | "project-manager" | "viewer";
  permissions: Permission[];
}
```

### POST /api/v1/auth/logout

Invalidates the app token.

### Frontend Environment Variables Required

```
NEXT_PUBLIC_AZURE_CLIENT_ID     — from Azure App Registration
NEXT_PUBLIC_AZURE_TENANT_ID     — Azure AD tenant ID
NEXT_PUBLIC_AZURE_REDIRECT_URI  — https://itpms.vercel.app/login
NEXT_PUBLIC_API_BASE_URL        — Laravel API base URL
```

### Azure App Registration Requirements

The Azure App Registration must have:
- Redirect URI set to `https://itpms.vercel.app/login`
- `openid`, `profile`, `email` scopes enabled
- Single-page application (SPA) platform configured

Frontend stores the app token in cookies (`auth_token`) and injects it as `Authorization: Bearer {token}` on all API requests.

### Authorization Header Injection

All service files automatically attach the Bearer token:

- **Client-side mutations** (POST/PUT/DELETE): Read token from `document.cookie` via `getAuthHeaders()` in `lib/services/api-helpers.ts`
- **Server-side reads** (GET): Read token from Next.js `cookies()` via `getServerAuthHeaders()` in `lib/services/server-api-helpers.ts`

If no token is present (user not logged in), requests proceed without the `Authorization` header — the backend will return 401.

## 8. WBS MODULE (Hierarchy Layer)

> "How is work decomposed?"

### Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/v1/wbs?projectCode=ITP-2026-0001` | Get WBS nodes for a project |
| GET | `/api/v1/wbs/{id}` | Get single WBS node |
| POST | `/api/v1/wbs` | Create WBS node |
| PUT | `/api/v1/wbs/{id}` | Update WBS node |
| DELETE | `/api/v1/wbs/{id}` | Delete WBS node |

### WbsNode Object

```typescript
type WbsLevel = "project" | "phase" | "deliverable" | "work-package" | "task" | "sub-task";
type WbsStatus = "not-started" | "in-progress" | "completed";

interface WbsNode {
  id: string;
  projectCode: string;
  parentId: string | null;
  code: string;              // "1.0", "1.1", "1.1.1"
  name: string;
  description?: string;
  level: WbsLevel;
  status: WbsStatus;         // Server-computed based on task progress
  plannedStart?: string;     // ISO 8601 date
  plannedFinish?: string;    // ISO 8601 date
  progress: number;          // 0-100, server-computed from tasks
  assignee?: string;
}
```

### Backend Rules

- Returns FLAT array (not nested) — frontend builds tree
- `code` is auto-generated by Laravel based on hierarchy position
- `parentId` references another WbsNode in the same project
- `status` is server-computed — NOT sent in create/update payloads
- `progress` is server-computed from tasks — NOT sent in create/update payloads
- Supports unlimited depth (per FR-PLN-002)
- Scheduling calculations (critical path, EVM) are backend responsibility
- Frontend only visualizes structure and progress
- Frontend sends `plannedStart` / `plannedFinish` (not `startDate` / `endDate`)

## 10. TASKS MODULE

> "What work needs to be done?"

### Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/v1/tasks?projectCode=ITP-2026-0001` | Get tasks for a project |
| GET | `/api/v1/tasks/{id}` | Get single task |
| POST | `/api/v1/tasks` | Create task |
| PUT | `/api/v1/tasks/{id}` | Update task |
| DELETE | `/api/v1/tasks/{id}` | Delete task |

### Task Object

```typescript
type TaskType = "planning" | "design" | "procurement" | "implementation" | "testing" | "training" | "documentation" | "closure";
type TaskPriority = "critical" | "high" | "medium" | "low";
type TaskStatus = "draft" | "not-started" | "in-progress" | "completed" | "on-hold";

interface Task {
  id: string;
  projectCode: string;
  wbsNodeId: string;         // Required — references WBS node
  taskCode: string;          // Auto-generated globally unique e.g. TSK-00001
  name: string;
  description: string;
  type: TaskType;
  priority: TaskPriority;
  status: TaskStatus;        // Server-computed based on progress
  duration: number;
  milestone: boolean;
  plannedStart: string;      // ISO 8601 date
  plannedFinish: string;     // ISO 8601 date
  actualStart?: string;
  actualFinish?: string;
  percentComplete: number;   // 0-100, updated via POST /tasks/{id}/progress
  assignments: TaskAssignment[];
  createdAt: string;
}

interface TaskAssignment {
  id?: string;               // Backend-generated
  userId: string;
  userName?: string;         // Backend-resolved
  role: string;
  allocation: number;        // 0-100
}
```

### Backend Rules

- `taskCode` auto-generated globally unique — counter must exclude soft-deleted records
- `wbsNodeId` is required — tasks must belong to a WBS node
- `status` is server-computed — NOT sent in create/update payloads
- Status transitions via explicit endpoints:
  - `POST /api/v1/tasks/{id}/hold`
  - `POST /api/v1/tasks/{id}/resume`
  - `POST /api/v1/tasks/{id}/cancel`
- Progress updated via: `POST /api/v1/tasks/{id}/progress` with `{ percentComplete, remarks }`
- `PUT /tasks/{id}` must NOT require ownership authorization — same open policy as WBS
- Single task response wrapped in `{ data: {} }`, list wrapped in `{ data: [] }`

### Integration Pattern

Services are split by server/client boundary:

```typescript
// Server-only query (lib/services/{module}-queries.ts)
import "server-only";
import { getServerAuthHeaders } from "@/lib/services/server-api-helpers";

export async function getItems(): Promise<Item[]> {
  const headers = await getServerAuthHeaders();
  const response = await fetch(`${API_BASE_URL}/items`, { headers });
  if (!response.ok) return [];
  return await response.json();
}

// Client-only mutation (lib/services/{module}.ts)
import { getAuthHeaders, handleUnauthorized } from "@/lib/services/api-helpers";

export async function createItem(values: FormValues): Promise<Item> {
  const response = await fetch(`${API_BASE_URL}/items`, {
    method: "POST",
    headers: getAuthHeaders(),
    body: JSON.stringify(values),
  });
  if (response.status === 401) { handleUnauthorized(response); throw new Error("Unauthorized"); }
  if (!response.ok) throw new Error((await response.json()).message);
  return await response.json();
}
```

All requests include `Authorization: Bearer {token}`. When Sanctum middleware is fully enforced, no frontend changes are needed.
